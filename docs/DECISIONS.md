- 2026-10-20 — Secrets for the core live in the host's macOS Keychain, account `fridolin`: `fridolin.tailscale.authkey`, `fridolin.b2.vault.key`/`.keyid`, `fridolin.b2.snapshots.key`/`.keyid`. `fridolin core start` (M1) reads them from there.
- 2026-10-20 — Tailscale: the policy file owns `tag:fridolin-core` and `tag:fridolin-node` (`autogroup:admin`). The core's auth key is reusable, not ephemeral, tagged `tag:fridolin-core`, 90 days; the node key waits for M2.
- 2026-10-20 — B2: buckets `fridolin-vault` and `fridolin-snapshots` in eu-central-003 (endpoint `s3.eu-central-003.backblazeb2.com`), private, SSE-B2, no object lock; both keep prior versions 30 days. One application key per bucket, restricted to it.
- 2026-10-20 — SQLite driver is `modernc.org/sqlite`. The DSN keeps the cgo driver's behaviour: `foreign_keys(1)`, `busy_timeout(5000)` (mattn's default; modernc has none) and `_time_format=sqlite` (mattn's text format, so old and new rows compare). whatsmeow's dialect name stays `"sqlite3"`.
- 2026-10-20 — The config version is `config.Version` in `internal/config/config.go` (PLAN.md calls it `currentConfigVersion`).
- 2026-10-20 — Windows process groups are `CREATE_NEW_PROCESS_GROUP | CREATE_NO_WINDOW` at start and `taskkill /T /F /PID` to stop, not the Job Object PLAN.md names: `exec.Cmd` has no hook between creating and resuming the child, so a job assigned after `Start` misses what the child starts first; and `KillProcessGroup(pid)` is called with nothing but a PID (after a crash too), so a job handle would have to live in package state, which `internal/platform` must not hold. Cost: taskkill walks parent PIDs, so it misses the children of a process that has already ended. Revisit when M2's node agent runs executors on Windows.
- 2026-10-20 — The Windows bridge lock is `LockFileEx` on one byte at offset 2^62 of `bridge.lock`, not on the PID: Windows locks are mandatory, and a second bridge must still read who holds it.
- 2026-10-20 — `platform.Exec` on Windows (no exec(2)) starts the same program as a child with the console and standard files, waits and exits with its status; each dashboard restart leaves one waiting parent.
- 2026-10-20 — On Windows the bridge reads no ACLs: the data dir's owner and mode checks say nothing, `O_NOFOLLOW` is `FILE_FLAG_OPEN_REPARSE_POINT` plus refusing a reparse point, and the hard-link count comes from `GetFileInformationByHandle` (`fsx.LinkCount`). Process start times are not read either, so no run is recorded and none is stopped after a crash; `--log-file` does not rotate (Go opens files without `FILE_SHARE_DELETE`); the tmux viewer and the folder dialog are unavailable.
- 2026-10-20 — M0 step 2 stops at a Windows build and `go vet`; running `claude` there (its `claude.cmd` shim through `cmd /C`) waits until Windows runs brains. `TestImportRules` now also checks the windows file set.
- 2026-10-20 — Windows in CI: a `go-windows` job (windows-latest, cgo off, no race detector, `go test -short`) beside the macOS/Linux matrix; `make vet` vets GOOS=windows too. Release archives for windows/amd64 and arm64 are `.zip` with `fridolin.exe`, cross-built on Linux.
- 2026-10-20 — The M0 data-layout step leaves `config.Version` at 2: it only adds the sections `core`, `vault`, `nodes` and `policy`, all off by default, and renames, removes or re-means no key, so a version 2 file keeps its meaning and needs no `configMigrations` step (PLAN.md assumed one; a bump would only make every older build refuse the file). A step comes with the first setting these sections supersede.
- 2026-10-20 — The new sections are live settings (`config.Live`), not restart (`Boot`) fields, while nothing runs on them; the code that starts the tailnet, the lease or the node port marks its fields `Boot` in `internal/config/fields.go`.
- 2026-10-20 — Data-dir paths come from `config.Layout` (`Boot.Layout()`); its folders are made lazily with 0700 by their feature (`config.EnsureDir`), never at startup. Packages that may not import config (platform, plaud) are handed the path: `platform.AcquireLock` takes the lock file's path, `plaud.Options.SiteDevices` the site's devices.json.
- 2026-10-20 — On Windows the bridge (the core) runs in the Linux container, as PLAN.md's platform matrix says; natively Windows runs only the node agent (M2). CI's go-windows job builds and vets everything but runs only the tests of packages that run natively (`WINDOWS_PACKAGES` in ci.yml); the bridge's own packages (app, backup, brain, claudecli, cli, config, fsx, httpapi, …) fail there on fixtures that write Windows paths into JSON unescaped and on HOME vs USERPROFILE, which matters only for a native Windows bridge. A package joins the list once its tests pass on Windows; the node agent's packages must be on it.

- 2026-10-20 — `fridolin doctor` (M0): checks are `DoctorCheck` values in `app.DoctorRegistry`, run against a `DoctorEnv` of injected lookups (LookPath, Run, Stat, ReadFile, FreeBytes, WriteProbe), so tests never touch the system; statuses are ok / missing / warn / fail, and only a `fail` of a check with `Required` set makes it exit 1. Required today: config loads, data dir writable, free disk (fails under 2 GB, warns under 20 GB), Claude CLI and the sandboxed brains' login (Codex CLI in Codex mode). Every other check carries the milestone that needs it (`Needed`) and is flipped to required in that milestone's pull request. Host secrets are checked for presence only (`security find-generic-password` without `-w`, exit 44 = missing; a 0600 file under `$XDG_CONFIG_HOME/fridolin/secrets/<service>` off macOS); doctor switches to `hostsecrets.Store.Has` once that package lands. The login check also finds `CLAUDE_CODE_OAUTH_TOKEN` in the launchd agent or systemd unit, by name only, since doctor runs in a shell whose environment is not the service's.
- 2026-10-20 — M3 vault library: `internal/cloud` (the `ObjectStore` interface, `cloud.Rclone` running `rclone rcat|cat|lsjson|deletefile` with `--config ""` so only the `RCLONE_CONFIG_*` variables the caller passes define the remote, and `cloud.Dir` as the fake) and `internal/vault` (index, policy, sync, watcher, evictor, hydrator, rebuild, search, brain scopes). Neither is wired into the bridge yet; that waits for the `vault` config section.
- 2026-10-20 — rclone's password obscuring is reimplemented in Go (`cloud.Obscure`, from rclone's MIT `lib/obscure`, credited in the file) so the crypt passwords never pass through an `rclone obscure` command line; a test checks both directions against the real binary when it is installed.
- 2026-10-20 — Cold object keys are the hot tier's relative paths; the crypt remote encrypts names and contents. The key `.fridolin-vault/manifest.json` is reserved: every Sync that changed something uploads it with each cold file's SHA-256, so `Rebuild` can verify cold files after vault.db and the `.cold.json` files are lost (crypt remotes offer no hashes).
- 2026-10-20 — Cold is complete, and nothing deletes from cold on its own: a hot file deleted after its upload becomes tier cold (listed in `.cold.json`), not a cold deletion. A file that never reached cold is forgotten. Deleting from cold will be an explicit call.
- 2026-10-20 — Eviction proof: row tier `both`, recorded hot hash = hash uploaded, cold object size = file size, and the file is moved aside (`.<name>.vault-evict-*.tmp`) and hashed again before it is deleted; `VerifyByDownload` also hashes the cold bytes. `New` puts back files a crash left aside.
- 2026-10-20 — Policy classes: cold-eligible files are all evicted (least recently used first) on every `Evict`; when hot usage is still above budget × (100 − headroom)%, files active only because they were used recently go next, oldest first. Pinned files, open-thread files, files hydrated within 7 days and markdown-first holds never go. Media with a companion, run logs older than 14 days, earlier months of `audit/` and `workspaces/` are cold-eligible even inside the 60-day window. Companions of `dir/stem.ext` are `stem.md|.txt`, `stem.ext.md|.txt`, `stem.transcript.md|.txt`, `stem.summary.md`. "Current month of audit/" is any `audit/` path with a `YYYY-MM` segment of the current month.
- 2026-10-20 — Last access is the later of the file's mtime and the vault's own reads (`Get`, `Touch`); file reads by brains outside the vault are not seen (no atime).
- 2026-10-20 — `Get` refuses with `vault.ErrInsufficientSpace` (`*InsufficientSpaceError`) when hot usage plus the file would exceed budget less headroom, or the injected free-space probe says the disk would keep less than the headroom; `GetOptions{AllowOverBudget: true}` is the "asked first" retry.
- 2026-10-20 — vault.db uses the bridge.db pragmas (`foreign_keys(1)`, `busy_timeout(5000)`, `_time_format=sqlite`), one connection, mode 0600, its own migrations counted in `vault_version`. Times are Unix milliseconds; mtimes nanoseconds.
- 2026-10-20 — M1 container: the image's build files live in `container/` (Dockerfile, compose.yaml, entrypoint.sh), with a Go package there that embeds compose.yaml, so `fridolin core start` writes the compose file of its own version to `<user config dir>/fridolin/compose.yaml` instead of looking for a checkout. The build context is the repository root, filtered by `.dockerignore` to an allowlist.
- 2026-10-20 — M1 container: base images `golang:1.26.8-bookworm`, `node:22.23.2-bookworm-slim`, `debian:bookworm-20261005-slim`; Claude CLI 2.1.303 from npm (its package installs the native build); restic 0.19.1, rclone 1.75.1, Litestream 0.5.17 from their GitHub releases with the published SHA-256 checked in the Dockerfile. ffmpeg, python3, bubblewrap, tini, git and curl from Debian.
- 2026-10-20 — M1 container: the build stage defaults to `CGO_ENABLED=0` for modernc.org/sqlite; a tree that still links mattn/go-sqlite3 builds with `--build-arg CGO_ENABLED=1` (same glibc in build and runtime).
- 2026-10-20 — M1 container: `http_listen` stays a loopback address; `fridolin run --container` binds its port on all of the container's interfaces instead, and compose publishes it as `127.0.0.1:8765:8765` only. The host side must keep the same port, because the Host guard answers only `127.0.0.1:<http_listen port>`.
- 2026-10-20 — M1 container: inside the image `FRIDOLIN_HOME=/data` (the volume) and `FRIDOLIN_CONFIG=/data/config.json`; the entry point writes a starter config with `data_dir: /data` before the first `run` only, so `core import` finds a fresh volume empty. The bridge itself does not read `FRIDOLIN_HOME` yet; the `fridolin core` commands do.
- 2026-10-20 — M1 container: brain folders in the container live under `/data/brains-folders/<name>/` so they move with the export; folders outside the data dir are listed in the export's manifest and warned about, not copied.
- 2026-10-20 — M1 secrets: the Claude token's keychain service is `fridolin.claude.oauth.token`. The container gets the B2 keys as `B2_VAULT_KEY_ID`/`B2_VAULT_KEY` and `B2_SNAPSHOTS_KEY_ID`/`B2_SNAPSHOTS_KEY`, the vault crypt passwords as `FRIDOLIN_VAULT_CRYPT_PASSWORD`/`..._PASSWORD2`, restic's as `RESTIC_PASSWORD`; code that runs rclone turns the B2 ones into `RCLONE_CONFIG_<REMOTE>_*` for rclone's environment only. `core start` makes only the age identity when missing; the vault and restic passwords are made by the M3 step that first needs them.
- 2026-10-20 — M1 secrets: keychain writes go through `security -i` with the command on stdin, so a value is never in argv; values are limited to `[A-Za-z0-9+/=._:@-]` so the quoting holds.
- 2026-10-20 — M1 export: format is tar, gzip (stdlib), then age (X25519, `filippo.io/age` v1.3.1), key `core/exports/<UTC time>.tar.gz.age`, with `core/exports/latest` holding the newest key as text. `manifest.json` is the first member, data under `data/`. Every `*.db` file is copied with `VACUUM INTO`. Excluded: `runs/`, `run-tokens/`, `media/`, `vault/`, `core/`, `brains/*/tmp|cache`, `node_modules/`, `*.lock`, SQLite sidecars, `*.tmp`, symlinks.
- 2026-10-20 — M1 import: staging is `<data dir>/core/import/<time>/` (same filesystem, so activation is one rename per entry); activation takes the data dir's instance lock and refuses a data dir with data in it unless `--force`, which moves it to `core/replaced-<time>/`. Imported files keep owner permission bits only. `data_dir` in the imported config is rewritten to the target; other outside paths are warned about.
- 2026-10-20 — M1 lease: the device id is per data dir (`core/device-id`, not exported), not per machine, so an imported copy and its source are different devices. The lease holder gives up when renewal has failed for `stale - renew` (4 minutes by default), one interval before another device may take it; a renewal that reads another device's record stops at once; clean shutdown writes `released: true`. Acquire's read-back after a 3 s settle is the only race protection, documented in the package.
- 2026-10-20 — M1 lease and export take a two-method store interface (Get/Put, missing key = `fs.ErrNotExist`) defined in their own packages until `internal/cloud` lands; the CLI has stand-ins (a folder store and an rclone store) behind `--store`.

- 2026-10-20 (M4): The run's MCP routes live under the brain API, as `GET /brain/mcp/tools` and `POST /brain/mcp/call`, guarded by the run token like `/brain/polls`; the scripts token is refused there, since it names no run. `fridolin mcp --run <id>` sends the id in `X-Fridolin-Run`, which must match the token's run (412 otherwise); identity comes from the token alone.
- 2026-10-20 (M4): The run token now records the run (brain, run id, chat and source of the message); a run is "delegated" when its message's source is `delegate`, which only the bridge sets, so a delegated run never gets `delegate` whatever its brain.
- 2026-10-20 (M4): Claude gets the run's MCP server from a per-run file `run-tokens/<brain>/run-<id>.mcp.json` (no secret in it, removed with the token) as a second `--mcp-config`, for every run, also with `inherit_claude_user_config`; Codex gets the same command through `-c mcp_servers.fridolin.*` with `env_vars` for `FRIDOLIN_API` and `FRIDOLIN_BRAIN_TOKEN_FILE` and a `tool_timeout_sec` above the longest delegate wait. The sandbox profile needed no change: runs could already execute `$FRIDOLIN_BIN`, read their run-token folder and reach the API.
- 2026-10-20 (M4): Grant targets must be configured brains (approved entries in `brain_dirs`), not running ones: a sub-brain whose folder goes missing must not take the core brain, and with it the DMs, down. Removing a brain removes it from the core's grants in the same config transaction.
- 2026-10-20 (M4): A delegated task is a message with source `delegate` on the chat `delegate:<core run id>` (one chat per core run, so the sub-brain sees earlier tasks of the same run and nothing else), carrying the delegation id as its message id. Such messages, and late results (`delegate-result`), are "handed in" like `/ingest`: never commands, never interrupting or replaced in interrupt mode, dropped (not kept) at shutdown.
- 2026-10-20 (M4): `delegate` waits 120 s by default, at most 600 s; past that the result goes to the core brain as a `delegate-result` message in the chat the core run answered, and the core's reply goes there. Failure reasons given to the model never carry the CLI's stderr.
- 2026-10-20 (M4): Audit lines are written by a small appender in `internal/app` (`<data>/audit/YYYY-MM.jsonl`, fields ts, kind, from, to, run, id, task, outcome, duration_ms), one line per delegation when it ends; M5's audit log may take it over.
- 2026-10-20 (M4): `read_memory` reads through `os.Root` component by component and refuses every symlink on the path, also ones inside the brain folder, since one inside `memories/` could lead to the brain's history or `brain.json`.
- 2026-10-20 (M4): `ask_user` and `request_approval` are listed for every run and answer with an error result saying they are not available yet; M5 fills them. The tool registry (`mcp.Registry`, keyed by name, with a per-run `Available` predicate) is where the vault tools register next.
- 2026-10-20 — M2 protocol: JSON text messages over one WebSocket (coder/websocket) at `/v1/node`, subprotocol `fridolin-node.v1`, every message an envelope with `"v": 1`; another version is refused rather than guessed at. Package `internal/nodeproto` is pure and has the decoder's fuzz target. The device ID is the first 12 hex digits of the ed25519 key's SHA-256, so it cannot be claimed without the key; the hello is proven with a signature over a 32-byte nonce bound to the protocol and the device ID.
- 2026-10-20 — M2 approvals: the registry keeps what a node declares and what the owner approved; the second stage is "approved" while the approval covers the declaration (each exec rule as it is, each root with no more access, limits no higher). A grown declaration is pending again, and meanwhile the node serves the intersection of both, so an edit to node.json does not cut off what already worked. Revocation keeps the record (the key stays refused) and drops every approval; a revoked machine rejoins as a new device with a new key.
- 2026-10-20 — M2 exec allowlist: rules are exact `argv[0]` (bare name or absolute path) plus optional whole-match regexes per argument (`null` any, `[]` none); shells and command runners (sh, bash, zsh, fish, cmd, powershell, pwsh, wsl, env, sudo, osascript, xargs, …) are refused by name on both sides whatever a rule says. Platform defaults are report-only commands. Paths are checked on the node only (the core cannot know the node's path rules) and opened through `os.Root`.
- 2026-10-20 — M2 node port: a plain `http.Server` on `nodes.listen` that takes a `net.Listener` (`nodes.Service.Serve`), so M1's tsnet listener can be handed in; it is not on the dashboard's mux and not in `routeInventory`. A bind failure is logged, not fatal (WhatsApp keeps running); `fridolin doctor`'s required `nodes-port` check reports it. `nodes.enabled` and `nodes.listen` became restart (`Boot`) fields.
- 2026-10-20 — M2 join codes: `fj-` plus 24 base32 characters (120 bits), single use, 10 minutes, stored as SHA-256 in `nodes/nodes.json`. The one-paste line names the core as the tailnet host name when `core.tailnet.enabled`, else the listen host, else this machine's host name.
- 2026-10-20 — M2 service: kardianos/service v1.3.0 (zlib licence). macOS launchd user agent `ai.fridolin.node`, Linux systemd user unit `fridolin-node`, Windows Service `fridolin-node` (system-level: the library has no per-user Windows services), each running `fridolin node run --state-dir <dir>`; a revoked agent idles instead of exiting, so the service manager does not restart it into the same refusal. The node's state dir is per OS (`platform.NodeStateDir`) and never the bridge's data dir.
- 2026-10-20 — M2 `!fleet` answers only in direct chats (a group gets a one-line refusal): it shows machine names and what each may run. Battery is reported on Linux only (sysfs); macOS and Windows would need IOKit/pmset or WMI, which is not cheap enough for a heartbeat.
- 2026-10-20 — M7's memory index is `memory/<brain id>.db` in the data dir, not `brains/<id>/memindex.db`: the sandbox lets a brain write its own `brains/<id>/`, and the index holds the provenance column the model must not write. Same for standing intents, `intents/<brain id>.json`. Both are made lazily (0700/0600).
- 2026-10-20 — Provenance rules (M7): history `in` lines are `owner` only with a WhatsApp message id, in a direct chat (not a group), from an allowed number; `/ingest`, `/send` and the bridge's hand-offs write no id, so a script or a brain cannot forge an owner line by naming the owner's number. The owner in a group is `untrusted`. Every `out` line, the brain's own replies included, is `system`: a reply may repeat what the brain read on a web page or in a search, and as `agent` it would launder that into recall (seen in the dev-mode try: a reply quoting search hits came back as an `agent` chunk); the bridge's schedule hand-offs (senders `intent`, `schedule`) are `system` too; votes, transcripts and everyone else `untrusted`. Notes in `memories/` are `agent` unless a notes comment's `source:` lowers them (URL, `web`, `untrusted`, `forwarded`, `attachment`, a transcript, or a history line that is not the owner's) or raises them to `owner` (every history anchor resolves to an owner line). A brain can thus only lower a note's class, or raise it to owner by citing what the owner really said.
- 2026-10-20 — Recall is per brain (`brain.json` `memory.inject`, approved like every manifest field), not a global setting, so `config.json` and its golden files stay as they were; off by default, so prompts and their goldens are unchanged unless a brain turns it on. Recall excludes what the prompt shows anyway (shown history lines by id; lines without an id in the same chat from the oldest shown on).
- 2026-10-20 — The index syncs lazily (before each recall and search) and every 30 seconds for brains with `memory` set, by size and mtime, re-hashing a changed file and reading only the appended part of the history (a 4 KiB tail hash before the old end tells an append from a rewrite). No fsnotify watcher yet. FTS5 query: the message's words (stopwords out, at most 32), each quoted, OR'ed, so nothing anyone writes is read as FTS5 syntax; rank `bm25(text 1, triggers 4) * (1 + 0.1 * importance)`.
- 2026-10-20 — PLAN.md's "`trigger.go` entries" for standing intents: `internal/trigger` gains `Schedule` (once, daily, weekly; there was no scheduler) beside the keyword `List`; an intent is one of the two. Intents are set through the brain API (`/brain/intents`) and only in a run that answers the owner's own direct message (allowed number, DM, WhatsApp or dev page, not handed in, not silent); the run token now remembers the run's message for that. Fired intents and the weekly consolidation reach the brain as a new message source, `chat.SourceSchedule`, which like `/ingest` is never a command and never interrupts.
- 2026-10-20 — `memindex.Search(ctx, memindex.Brain, q, SearchOptions)` is the call the MCP server (M4) wraps for its memory tool; `memindex.Recall` is the injection rule. `fridolin doctor`'s `memory-index` check is required (M7 gate): it runs `memindex.SelfTest` (the gate on a scratch brain) and checks each enabled brain's index is up to date; it applies only when a brain sets `memory`.
- 2026-10-20 (M3 wiring): The vault's hot root is the data dir itself, with an allowlist (`vaultLayout` in `internal/app/vault_layout.go`): `config.json`, `secrets/`, `audit/`, `vault/` (documents, workspaces), the media folder when it is in the data dir, and brain folders inside the data dir (the container's `brains-folders/`). `bridge.db`, `vault.db`, their sidecars and Litestream's `.<db>-litestream/` are never file-synced (Litestream and `VACUUM INTO` copies cover them); `brains/` (per-brain CLI state), run tokens and records, tokens, sessions, `rclone/`, `google/`, `plaud/`, `otp/`, `site/`, `tsnet/`, `nodes/`, `core/`, `backup/` and lock files stay out; restic's nightly snapshot covers them. Brain folders outside the data dir (native installs) are not vault files; the snapshots cover them. The policy's `workspaces/` rule also matches `vault/workspaces/`.
- 2026-10-20 (M3 wiring): A brain's vault paths are `vault/documents/<id>/`, its media inbox `media/<id>/` (when the media folder is in the hot root) and its folder when that lies in the data dir. A core run adds the paths of the brains its manifest grants `files` (running brains only, never in a delegated run).
- 2026-10-20 (M3 wiring): `vault_get` answers with the file's own path when it lies in the run's folder or inbox, which its sandbox reads; otherwise (a document in the data dir, another brain's inbox) with a copy (not a hard link, so a write cannot change the vault's file) in `brains/<caller>/tmp/vault/<vault path>`, the run's TMPDIR. `vault_put`'s `from` must be a file in the run's folder, inbox or temp folder, opened through `os.Root`, since the bridge reads it outside the sandbox. Vault tools also take absolute paths in the hot root.
- 2026-10-20 (M3 wiring): An open thread is a message a brain is running or has waiting: its attachments (`Inbound.Media`) are the open-thread paths (`Brain.OpenMedia`), kept hot by the policy; before a run starts, the bridge brings back those of its message that went cold (`BrainHooks.Hydrate`, reached through `brain.InputRules.Hydrate`), within the budget. With M7 the brain hydrates first and then builds the prompt, with what the memory index recalls, so the prompt never names a file the run cannot read yet.
- 2026-10-20 (M3 wiring): The vault settings stay live: a change to the `vault` section stops the vault service and starts it again with the new settings (no restart field), and a brain added or moved changes the hot root's allowlist at once.
- 2026-10-20 (M3 wiring): Credentials come from the environment (the names docs/CORE.md gives the container); a native bridge (`fridolin run` without `--container`) falls back to the host's secrets and makes the crypt passwords and restic's password there when missing (32 random bytes, base64url), but only after checking the cold tier's raw `vault/` folder is empty, and that `restic cat config` says no repository exists (exit 10) for the new password; it logs a recovery-sheet reminder without values. Inside the container nothing is made.
- 2026-10-20 (M3 wiring): restic: repository `b2:<snapshots_bucket>:restic` (`B2_ACCOUNT_ID`/`B2_ACCOUNT_KEY` from the snapshots key), cache in `core/restic-cache`, host `fridolin-core` for every snapshot (so retention spans a move), tags `fridolin` plus `nightly` or `hourly`; nightly after 03:00 local (or 26 h after the last), hourly for brain folders and `audit/`; `forget --prune --group-by host,tags` with 24/14/8/12 after each nightly; `check` weekly, `--read-data-subset=5%` monthly; one restic job at a time.
- 2026-10-20 (M3 wiring): The mass-deletion guard for snapshots: a snapshot whose file count fell from the previous snapshot of its kind by more than the Drive backup's limit (`snapshot.MassDeletion`, the same thresholds as `backup.maxDeletions`) sets a deletion hold that skips pruning until `POST /api/vault/prune/allow`.
- 2026-10-20 (M3 wiring): The Drive restic repository is `rclone:<backup.remote>:fridolin-restic` through the bridge's own `rclone/rclone.conf` (`RCLONE_CONFIG`, `-o rclone.program=`), same password as the B2 repository, initialised with `--copy-chunker-params` from it, filled by a weekly `restic copy`. compat: the old Drive sync's scheduled run stops only once that copy has completed once while the vault is on (`backup.Options.Superseded`), so the Drive backup never has a gap; manual runs and restores keep working.
- 2026-10-20 (M3 wiring): Litestream runs as a supervised child (`snapshot.Litestream`) with a generated config (0600, in `core/`, removed on exit, no keys in it) replicating `bridge.db` and `vault.db` to `<snapshots_bucket>/litestream/<db>` over B2's S3 endpoint (region from `vault.endpoint`, path style); the snapshots key goes in `LITESTREAM_ACCESS_KEY_ID`/`LITESTREAM_SECRET_ACCESS_KEY`.
